01 — Contexto

Qué es QDD Sky

Es una capa operativa —también llamada agent harness— que se instala en un proyecto y organiza lo que el agente de IA necesita para trabajar en Sky.

1. Modelo

Razona y genera respuestas. Por ejemplo, GPT-5.6 Sol o Claude Opus.

2. Agente

Utiliza el modelo y puede leer archivos, ejecutar comandos y usar herramientas. Por ejemplo, Codex o Claude Code.

3. Harness

QDD Sky especializa al agente con reglas, conocimiento, automatizaciones y workflows para trabajar en Sky.

02 — Componentes

Qué contiene QDD

Reglas Definen qué puede hacer QDD, qué debe comprobar y cuándo necesita autorización.
Conocimiento Información sobre los sistemas, sus relaciones y las formas de trabajo del equipo.
Skills Instrucciones para ejecutar una tarea específica o un workflow completo.
Scripts Automatizan tareas que deben ejecutarse siempre de la misma manera.
Agentes especializados Realizan revisiones independientes en etapas definidas del proceso.
Workflows Encadenan varias tareas hasta alcanzar un resultado definido.

03 — Instalación

Instalar QDD Sky como plugin

La rama release contiene el paquete preparado para Claude Code, Codex y OpenCode. La instalación registra el catálogo y activa el plugin principal.

1
Confirmar acceso

La cuenta debe tener acceso al repositorio privado qurable/QDD-Sky y Git debe estar autenticado por SSH o mediante gh auth setup-git.

2
Elegir el runtime

Seleccionar una pestaña y ejecutar los comandos exactos para ese entorno.

3
Activar el core

Instalar qdd-sky. Los paquetes opcionales aparecen en el mismo catálogo y se agregan por separado cuando son necesarios.

Codex release · 0.1.0-beta.1

Agrega el catálogo privado desde la rama release y luego instala el plugin principal. 

codex plugin marketplace add git@github.com:qurable/QDD-Sky.git --ref release
codex plugin add qdd-sky@qdd-sky
Disponible después de instalar
skills _qdd-docs agents hooks config

El runtime recibe workflows, capacidades y conocimiento en la estructura que necesita para utilizarlos directamente.

04 — Workflows

Workflows disponibles

Un resultado completo utiliza un workflow. Una tarea puntual utiliza una instrucción específica. El código de cada tarjeta indica el estado que puede devolver.

05 — Ejemplo de ejecución

“Resuelve VC-1303”

El pedido activa el workflow de resolución de una iniciativa.

Leer y precisar el pedido
  1. Busca el ticket en Jira y abre el material relacionado.
  2. Lee descripción, DoR (Definition of Ready), criterios de aceptación, comentarios y enlaces.
  3. Separa requisitos confirmados, supuestos, contradicciones y datos pendientes.
  4. Determina la complejidad e identifica los repositorios e integraciones que pueden verse afectados.

06 — Pedidos puntuales

Ejemplos de pedidos puntuales

También se pueden pedir tareas acotadas que no requieren ejecutar uno de los workflows anteriores.

Entender un flujo

“Explícame cómo funciona el flujo de pago con DEUNA.”

Revisar una entrega

“¿Qué cambios están incluidos en este tag de deploy?”

Investigar un caso

“Busca en los logs qué ocurrió con esta reserva y hasta dónde llegó.”

Refinar un pedido

“Revisa este DoR y señala qué información falta o se contradice.”

Evaluar evidencia

“Revisa estas evidencias y dime qué resultado demuestran realmente.”

Mejorar documentación

“Revisa este documento y ajusta las partes que no se entienden fácilmente.”

Resultado

QDD utiliza solo las capacidades necesarias y termina al entregar la respuesta solicitada.

07 — Cuándo interviene el usuario

Cuándo necesita una respuesta

La diferencia es si QDD puede ejecutar y comprobar el siguiente paso dentro del alcance autorizado.

NO NECESITA RESPUESTA

Continúa de forma independiente

Avanza mientras el siguiente paso cumpla estas condiciones:

  • Está incluido en el pedido y no cambia su alcance.
  • Puede consultar el contexto y la evidencia necesarios con los accesos disponibles.
  • La acción es rutinaria, reversible y su resultado puede comprobarse.
  • Puede revisar y corregir el resultado antes de continuar.
NECESITA RESPUESTA

Se detiene ante un bloqueo

Cualquiera de estas condiciones impide que continúe de forma independiente:

  • El usuario debe elegir entre alternativas que cambian el alcance, el comportamiento o el resultado.
  • Falta un dato, acceso, permiso o evidencia indispensable.
  • La siguiente acción no estaba incluida en el pedido o requiere autorización explícita.
  • La acción es sensible: fusionar un MR, operar en PROD, pagar, reiniciar, revertir, reenviar eventos o publicar.
